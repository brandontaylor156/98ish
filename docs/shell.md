# Desktop shell and phone platform
Shared systems every program relies on: audio, dialogs, menus, phone hold menus, touch controls, the 98ish keyboard, drop-downs, user profiles, lock screen, Control Panel, accessibility, search, Help, and the simplicity pattern. Moved from CLAUDE.md on 2026-10-05.
## Shared systems
  - **Audio** (`client/src/utils/audio.js`): one AudioContext and `createBus`, following the taskbar volume and mute.
  - **Draggable dialogs** (`shared/Dialog.jsx` + `hooks/useFloating.js`). During a drag the popup follows the pointer through left/top written once per frame from a containing-block origin measured at the press (which also re-reads where the box is drawn, so nothing that moved it can cause a jump); letting go measures and moves nothing (the older translate-then-commit release snapped the box elsewhere on a real iPhone, not reproducible in Chrome or Playwright WebKit). Ends on pointerup/pointercancel/lostpointercapture (never stuck). `?dragdebug=1` (remembered per browser; `=0` off) shows an on-screen log per release: drawn before -> after -> 300 ms later, plus refits. Phones: the title bar takes the gesture (`touch-action: none`, non-passive touchstart/touchmove preventDefault, no callout/selection, no long-press menu), a second finger can't take over, a finger's press never focuses a text field (it raised the 98ish keyboard mid-drag), and the whole popup stays inside the safe areas, above the taskbar and above the 98ish keyboard (it refits when `html.kb-open`/`--kb-h` change; the keyboard no longer `translate`-lifts `[data-floating=on]` boxes, which used to jump back when it hid). Mouse dragging is unchanged (60 px of title bar kept off-edge). Browser tests: `drag-phone.mjs` (CDP touch), `drag-webkit.mjs` (Playwright WebKit iPhone 14, iOS-ordered synthetic touch pointer events: `npx playwright-core install webkit`), `drag-desktop.mjs`; each checks no snap at release, a frame later and 300 ms later. **Where popups open (2026-10-07):** centered popups (`center: true`: every `Dialog`) open in the middle of what you can see: the visual viewport (`visibleViewport()`: the phone's own keyboard and Safari's bars shrink only that) above the taskbar and the 98ish keyboard, intersected with their window on a computer. They stay centered while they grow, the keyboard comes or goes or the phone turns, until the user drags one (`moved`); before, a dialog kept its top-left corner, so one whose content arrived after it opened grew toward the bottom right, and a turned phone left it at the old spot. Every popup on a phone, and dialogs everywhere, get an inline max size of the free screen; a floating `.dialog` is a flex column whose body scrolls, its `.dialogButtons` stick to the bottom (OK/Save always reachable) and the focused field is scrolled into view clear of them (`revealFocus`); FileDialog's file list gives up its room first (Save As in landscape had File name and Save under the keyboard). It also ends a drag and refits on `visibilitychange`/`orientationchange`/`INPUT_RESET` and visual-viewport changes; `el._floating.refit()` is public for the input guard. Browser scripts `center.mjs` (phone portrait, grown, turned; desktop grown and moved by hand), `wp-explore.mjs [landscape]`, `save-apps.mjs`.
  - **Taps that stop working** (`utils/inputGuard.js`, installed in `main.jsx`; test `node --test client/src/utils/inputGuard.test.js`, browser script `freeze.mjs`). On `visibilitychange`, `pageshow` (bfcache) and `orientationchange` it fires `INPUT_RESET` (`onInputReset(fn)`): popup drags end and come back on screen, desktop icon drags, long presses (`useLongPress`: a press the page lost no longer opens its menu later) and the 98ish keyboard's held keys (a held Delete kept deleting) are dropped; click swallowers go through `swallowNextClick` and are released; a page the phone scrolled goes back to 0. Modal layers (`MODAL_LAYERS`: `.desktopDialogLayer`, `.globalMenuLayer`, `.shellLayer`, `.runLayer`, `.powerDim`, `.dialogBackdrop`, `.tm-modal`) whose dialog can't be seen (less than 24x24 px on screen) get `data-input-stuck` (main.css: `pointer-events: none`, its dialog still takes taps); checked 400 ms after each reset and on a tap that lands on a bare layer. Three taps on buttons in a row with no click reset by themselves. `?tapdebug=1` (remembered, `=0` off) shows the last 10 lines above the taskbar: each tap's `elementFromPoint` and its layer, "no click after the tap", resets, stuck layers, resizes; also kept in sessionStorage `98ish.tapLog` and `window.__tapLog`. Also: sounds can't throw out of a button (`systemSounds.play` and `audio.wake` guarded), and `html.os-locked` is only set while the lock screen is up (Log On after a lock was hidden by it). Root cause of the owner's report not confirmed (see CLAUDE.md Known issues).
  - **Printing** (`utils/print.js` `printDocument({ title, html, css, page })`, `shared/PrintDialog.jsx`; test `node --test client/src/utils/print.test.js`, browser script `print.mjs` with PDFs): the document's own copy goes in `body > .os-print`, `body.os-printing` hides everything else for print and main.css un-pins html/body (their `position: fixed` printed one cut-off page), then `window.print()` straight from the tap (iOS opens its print screen only inside a user gesture; AirPrint or Save to Files). Removed on `afterprint` or the next print. WordPad (Letter, 1 x 1.25 in.), Notepad (text with its name on top), Paint (the picture, landscape when wide), Help topics and Appward records/reports (no more pop-up window or hidden frame: neither prints from an iPhone Home Screen app). Escape user text (`escapeHtml`) or sanitize it before it goes in.
  - **Taskbar safe areas** (2026-10-07): the taskbar pads by `env(safe-area-inset-left/right)` and the phone Start menu sits inside them, so with the phone on its side Start, the taskbar buttons and the tray no longer run under the notch and rounded corners (`notch.mjs` emulates the insets with CDP `Emulation.setSafeAreaInsetsOverride`; `taskbar.mjs` checks Quick Launch/Show Desktop at desktop-view sizes).

  - **Menu bars** (`shared/MenuBar.jsx`): a drop-down taller than the room under it (Pickleball's Options menu on a phone, above all in landscape) gets `is-scroll` + a max-height and scrolls inside the window instead of running off its bottom (2026-10-05; rows past the edge were unreachable); a submenu inside a scrolling menu drops down over its row. Phones get 34px rows. Browser scripts `pb-menu.mjs [chromium|webkit] [landscape]`, `pb-menu-scroll.mjs`.
  - **No phone "hold" menus** (`main.css` "No phone hold menus" block + `utils/touchGuard.js`, installed in `main.jsx`; test `node --test client/src/utils/touchGuard.test.js`). THE RULE: everything is `user-select: none` + `-webkit-touch-callout: none` (set on `body`; Safari needs the `-webkit-` prefixes, always write both), so a hold never shows the loupe, Copy/Look Up or Save Image. Allowed automatically: text inputs, textareas, contenteditable. Opt a reading area in with `data-selectable` (or class `selectable`); `data-selectable="mouse"` = mouse only (Messenger's transcript, where a held message opens reactions; their box has Copy); `data-selectable="false"` off again inside one; `.dialogBody p` (error/notice words) is allowed. Buttons, labels, title bars and `[role=button|menuitem|tab]` are never selectable, even inside an area. Pictures/canvases/video never offer Save Image or drag out (Photos has Save/Share menus). Opted in now: Mail text, Help topics, Address Book details, Calendar event notes/location, Notepad/WordPad, game chat and logs, Calculator display, Task Manager messages. Since iOS 18 a tap followed by a hold shows the loupe even over `user-select: none` (WebKit bug 296492), so TOUCH SURFACES cancel `touchstart`: mark an element `data-touch-surface` (or add to `SURFACE_SELECTOR`: TouchControls zones/buttons and Pickleball's court are listed there). Only on things driven by pointer events (a cancelled touchstart means no `click`) that don't scroll by dragging (Minesweeper's board scrolls, so it relies on CSS). Marked: Shred, Hover, Downhill, SPECTRA, Tetherball, Our Pet's catch game, Echo Pads, Zap It!, Boom Frenzy's field, Tetris while swiping. A finger's `contextmenu` (Android) outside fields is cancelled even if a handler only stops it. iPhones send no `contextmenu` on a hold, so app menus need `useLongPress` (Photos tiles now have it). Audit scripts `lp-audit.mjs` (WebKit, every program: styles at title bar/buttons/pictures/fields/text) and `lp-behave.mjs` (Chrome: long-press menus, Minesweeper flag, reactions Copy, touch surfaces).
  - **Touch controls** (`shared/controls/`). The editor panel takes a game's own options through the `settings` prop (exported `Check`/`Slider` match its look). The Customize Controls panel drags by its title bar (mouse or finger, pointer capture, `touch-action: none`, kept inside the game area; the ▲/▼ button still snaps it to top/middle/bottom). A control's `retired: { portrait: [old defaults] }` moves players whose saved layout still holds an old default spot to the new one (`mergeLayout` + `retiredRects`, test `node --test client/src/components/shared/controls/layout.test.js`).
  - **98ish phone keyboard** (`shared/keyboard/`; design in `docs/keyboard.md`). Enter's label (`fields.js` `enterLabel`): the field's `enterKeyHint`, else search/url/multi-line, a dialog's default button (`data-kb-enter` from `Dialog.jsx`), Go in other forms, else Enter; never "Done" by itself. `enterKeyHint="next"` moves on without submitting. While it's up on a phone, window status bars hide (`data-kb-status="keep"` keeps one; YouTube's "Done" status read as part of the keyboard) and chat transcripts stay at the newest line. `data-kb-auto` + `requestKeyboard(el)` (`native.js`) bring it up with no tap (Speed Typist's race box at GO and when the race comes back into view). Browser scripts `kb2-*.mjs` (labels, chat/IM/Mail/dialog/game-chat layout, Speed Typist), sound on a phone `snd2-phone.mjs`.
  - **98-style drop-downs and date/time pickers** (`shared/select/`, `SelectHost` mounted once in App.jsx): takes over every `<select>` and `input[type=date|time|datetime-local|month]` with no change at the call sites. Touch: the tap's `touchend` is cancelled (no focus, so no iOS picker); a list drops down under the field like the mouse one (40px rows on phones; the owner wanted a real drop-down, 2026-10-04) and only date/time pickers open as a 98 bottom sheet (older `sel-*` scripts that wait for `.selSheet .selList` need `.selDrop .selList`); mouse: the `mousedown` is cancelled and a list/calendar drops down (date fields keep typing; only their button opens the calendar); keys: Alt+Down/F4/Space. Choices go through the native value setter plus `input`/`change` events, so React state updates. Opt out with `data-native-select`; `multiple`/`size>1` lists stay native. **Touch screens (2026-10-07):** the owner still saw the iOS wheel/date picker (Date/Time, Calendar), so on `(hover: none) and (pointer: coarse)` the fields themselves are `pointer-events: none` (Select.css): the phone never gets a tap on them, the tap lands on their row or label and `controlAt(target, x, y)` (fields.js: the target's field, or a field inside the target under the point; never one behind another element) opens ours. Browser script `pickers.mjs` (Date/Time month + zone, Clock alarm, Tasks due/date/time: the 98 picker opens and the native field never gets the touch or focus). **One tap, several events (2026-10-05):** a real iPhone can deliver a tap on a select as touchend + made-up mouse events + focus (when the touchend can't be cancelled) or focus during the touch; each path used to toggle, so the list opened and shut at once. Now a toggle within 500 ms of opening is the same tap (`justOpened`), and mouse events right after a touch on the field (`recentTouchOn`) open as a touch. Emulation's clean tap never showed this; `pb-ios-seq.mjs` dispatches those event orders. Tests: `select.test.js`, browser scripts `sel-*.mjs`, `pb-dd.mjs [chromium|webkit]`, `pb-ios-seq.mjs`.
  - **User profiles** (`utils/users.js`): each person on a device has their own desktop, drive, settings and scores. THE STORAGE SEAM: `userKey("98ish.x")` maps a key to the logged-on person's (`98ish.u.<id>.x`; the default user keeps the plain keys, so a device's existing data is the first user's). `utils/userStorage.js` (imported first in `main.jsx`) applies it to localStorage getItem/setItem/removeItem, so plain localStorage code needs nothing. Any other store (IndexedDB) must call `userKey()`/`keyPrefix()` itself and register `onUserRemoved(fn)`. Device keys (`GLOBAL_KEYS`: `98ish.users`, `98ish.currentUser`, `98ish.lock`...) stay shared. Switching users reloads the page (`switchUser`).
  - **Lock screen** (`utils/lock.js`, `utils/lockCrypto.js` PBKDF2-SHA256 600k with a random salt, `utils/lockTimers.js`, `OS-specific/lock/`): PIN or password per user (hash in the user's profile), Start > Lock Computer, Win+L / Ctrl+Alt+L, idle wait (`lockAfter`), screen saver (`lockOnSaver`), reopen after the wait; state in `98ish.lock` survives reloads. Wrong tries wait 5s, 15s, 45s... While locked the desktop stays mounted but hidden (`html.os-locked`), keys are stopped in lock.js, arrivals call `notifyLocked()` ("New message" only), and CallManager hands the ringing call to the lock screen (Decline at once, Answer after the PIN). "Forgot PIN?" signs in to the linked 98 Messenger screen name (`aim:verify`, no session) or, with none linked, removes the lock after a warning. Settings: Start > Settings > Passwords and Users (`applets/passwords/`). Log On (`lock/LogOn.jsx`) picks or creates users.

## Simplicity (every program; details, audit and remaining candidates in `docs/simplicity.md`)
- Each program opens to a **baseline view**: the 1-3 things most people do, in big clear controls. - Toolbars may show a button only while it can be used (Help's Forward, IE's Stop on phones, My Computer's Cut/Copy/Delete on phones once something is selected); formatting bars sit behind **Aa** (IM window, WordPad).
