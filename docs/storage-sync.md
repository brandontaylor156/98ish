# The 98ish drive, persistence and file sync
Moved from CLAUDE.md on 2026-10-05.

## Storage and sync
- **Vercel Blob checked against the real store (2026-10-04):** from a page at https://98ish.vercel.app in real Chrome, a presigned PUT (headers only `x-api-version`, `x-vercel-blob-access`, `x-content-type`: Vercel's CORS allow-list doesn't include `x-add-random-suffix`/`x-allow-overwrite`, and the signed URL already pins them) and a presigned GET work (`Access-Control-Allow-Origin: *`); unsigned GETs, oversize PUTs and overwrites are refused; `head()` reports the size. Scripts: scratchpad `blob-smoke.cjs`, `blob-browser.cjs` (token pulled with `vercel env pull` into a temp file, deleted at once, never printed).
- **The drive** (`utils/fs.js`, `utils/driveStore.js`): the synchronous tree API is unchanged, but the drive is kept in IndexedDB (database `98ish-drive`: `meta` holds the folder index with small files inline, `contents` holds big texts keyed by a content hash, so copies share storage and unreferenced contents are deleted in the same transaction). `main.jsx` renders nothing until `fsReady` (a "Loading your files..." screen after 300 ms). `navigator.storage.persist()` is requested at start.
  - Big contents load on demand: `file.textContent` returns "" until loaded (and starts loading); use `await readContent(file)` (or `peekContent`) for anything that sends, edits or copies contents; `file.loaded`, `file.size`, `file.head` (first 48 characters: what kind of data URL), `file.textLength`, `file.thumb` (192 px JPEG of big pictures, made in the background) work without loading. Memory cache: 48 MB of text on phones, 160 MB on computers.
  - `saveNow()` and `writeAndSave()` are async (resolve false on a full disk; callers await them). Saves run 40 ms after a change: a browser drops IndexedDB writes started while a page closes, so the window stays tiny.
  - First start after the update moves the old localStorage drive (`98ish.fs.v1`): one transaction, read back and compared file by file, then marked (`98ish.fs.migrated` + IndexedDB `meta.migration`). The old copy stays 3 days. A failed move changes nothing and is retried next start (meanwhile the old drive works). Without IndexedDB (some private windows) the old 5 MB localStorage drive is used, and `StorageNotice` says so; if IndexedDB was used before but won't open, the drive opens read-only-ish ("changes won't be saved").
  - Drive C: Properties (My Computer) shows used/free/capacity with the Win98 pie (`fileExplorer/DriveProperties.jsx`); Camera and Photos show free space; `DISK_FULL` is the shared "Drive C: is full" text.
  - Backup builds the file in pieces (`writeDriveJson`, `createBackupBlob`); Restore and `importDrive` put everything back if it doesn't fit.
- **Persistence ("photos must PERSIST")**: the device copy can vanish (Safari evicts a site's storage after ~7 days without a visit unless it's a Home Screen app; any browser may evict without `persist()`), so file sync is the safety net:
  - **Sync is ON by default**: `98ish.drive.sync` prefs carry `told`; nothing saved (or an old-version `enabled:false` without `told`, which every sign-off used to save) means on, and the first sign-on sets `told` and `turnedOn`, which `backup/DriveSync.jsx` shows once as a 98 dialog ("File sync is on", OK / Settings...) plus a Notification Center item. Turning it off in Backup is remembered (`told: true`). Old browser suites that click `label[for=bk-sync]` to turn sync ON must now click only if `#bk-sync` isn't checked.
  - A change uploads ~4 s later (`PUSH_DELAY_MS`) and on `visibilitychange`; a new device (or a wiped one) pulls everything at sign-on.
  - `navigator.storage.persist()` is asked at start and again on the first `pointerdown` if refused; the answer is `storageInfo().persisted`, shown in Drive C: Properties and Control Panel > Storage (with an iPhone 7-day hint when not on the Home Screen).
  - **Guests**: `utils/keepSafe.js` (pure, `keepSafe.test.js`) + `shared/KeepSafe.jsx` (`useKeepSafe`, `<KeepSafe place>` note with Sign On... / Backup... / close for 30 days, `98ish.keepSafe`): Camera after a photo, Photos, My Computer's status bar (`.fxKeepSafe`), Control Panel > Storage ("Keep your files safe").
  - Capacity: photos are JPEG <= 2048 px and `MAX_CHARS` 560,000 (~400 KB; `photos/photoMath.js`), stored as binary on the server, so 100 MB is ~250-300 photos per account and a couple fits in 200 MB of Atlas's 512 MB; `DRIVE_SYNC_TOTAL_MB` guards the rest.
- **File sync** (`utils/driveSync.js`, decisions in `utils/syncPlan.js`; server `server/drive/sync.js` + `syncStore.js` at `/api/drive/sync`): per-file sync of chosen top-level folders (default My Documents, My Pictures, Desktop; never Programs/Windows/Bookmarks) for the signed-on 98 Messenger account. Entries are keyed by path with a server revision counter; devices pull changes since their last revision, upload missing contents (checked against their hash), then push changes with the revision they were based on. Both changed: both kept, this device's copy renamed "name (from iPhone)". Deletes are tombstones and land in the other device's Recycle Bin. Settings and online usage are in Backup ("Sync with 98 Messenger"); status in the taskbar tray (`backup/SyncTray.jsx`) and My Computer's status bar.
  - On by default: a device with nothing saved turns sync on at its first sign on and says so once (`told`). A device that saved "off" under an older version (which saved "off" on every sign off, chosen or not) is NOT turned on silently: the next sign on asks once ("Turn on file sync?" Turn On / Not Now, `ask` in the prefs, `answerSyncAsk`); either answer is final (Backup can still change it). Browser test `del-ask.mjs`.
  - Signing on gives the device its own sync token (POST `/device`, stored hashed, 60 days, 10 per account), so a device bumped by a sign-on elsewhere keeps syncing; signing off on purpose or turning sync off forgets it.
  - **Online storage bucket** (`server/drive/bucket.js`, on with `BLOB_READ_WRITE_TOKEN`; `@vercel/blob` SDK): contents go to Vercel Blob at `u/<HMAC of account>/<contentKey>` (private, content-addressed, type always `application/octet-stream`; the real type is in the record) and MongoDB keeps only records (`syncblobs` with `store: "bucket"`, `path`, no `data`). `/state` says `direct: true`; the client (`driveSync.js` `uploadDirect`/`downloadDirect`) does `POST /upload` (quota + 30-min reservation, presigned PUT: size and type pinned, no overwrite, 10 min) -> PUT -> `POST /commit` (server `head()`s the size), and `POST /urls` (presigned GETs, 5 min, own account only, asked for 20 at a time). Anything that fails falls back to the old `/blob` routes, which also work with the bucket (server reads/writes it). FREE ONLY: every op is counted in MongoDB `blobusage` (one doc per UTC day) BEFORE it happens, against rolling 31-day budgets under Vercel Hobby's free limits (1 GB stored, 2,000 advanced ops, 10,000 simple ops, 10 GB transfer); when one is used up, uploads/downloads answer 429 "Online storage is resting until <date>" and files wait on the device. Vercel saying the store is suspended rests everything a day. Background upkeep (every 10 min, 1 min while busy; 70% of each budget): expired reservations dropped, old MongoDB contents moved 10 at a time (first 20 read back and compared, the rest size-checked; MongoDB copy kept 7 days, then `data` unset), weekly list for stray objects (no record, over a day old). Delete My Account / Delete Online Files delete objects by their recorded paths (del is free). Public numbers: `GET /api/drive/sync/status`. Hobby usage is shared with the website, so the budgets leave room. Presigned GETs from a browser to `*.private.blob.vercel-storage.com` are not yet tried on real Vercel: if CORS blocks them, the client falls back to `/blob` (server egress) automatically.
  - **Shared Albums** (`server/albums`, see `docs/apps.md`) use the same bucket under `a/...`: at most `ALBUM_SHARE` 0.25 of each budget (scope "albums"), 150 MB total (`ALBUM_TOTAL_MB`), 40 MB per account; their bytes count in the 750 MB total via `addStored`. So the bucket's split is roughly: file sync (whatever is left), IM media <= 200 MB / half the ops, albums <= 150 MB / a quarter of the ops.
  - MongoDB collections `syncaccounts`, `syncentries`, `syncblobs` (data URLs stored as binary, other text deflated; with a bucket only records), `syncdevices`, `blobusage`. Quota and file size from the env vars above; 20,000 entries per account; per-account rate limits and 300 MB upload per 10 minutes. The old whole-drive copies (`drives`, `/api/drive`) still work and are converted into synced files the first time an account syncs.
- **Tests:** `node --test client/src/utils/driveStore.test.js` (migration with a tiny fake IndexedDB, `utils/fakeIndexedDb.js`), `client/src/utils/syncPlan.test.js`, `server/drive/test/sync.test.js` and `bucket.test.js` (in `npm test`; the real SDK against `server/drive/test/fakeBlob.js`, a fake Vercel Blob that checks presigned signatures; plus the S3 signer against AWS's SigV4 examples). Browser: run `node server/drive/test/fakeBlob.js 9364 vercel_blob_rw_teststore_secret`, start the server with `BLOB_READ_WRITE_TOKEN=vercel_blob_rw_teststore_secret VERCEL_BLOB_API_URL=http://127.0.0.1:9364/api/blob BLOB_STORE_URL=http://127.0.0.1:9364/store`, then `b2-e2e.mjs` (desktop + iPhone emulation; checks no `/blob` requests). Browser suites `stor-*.mjs` (migrate, photos, backup, sync, fallback). In dev, `window.__drive` (`info()`, `exportDrive()`, `readContent`, `writeAndSave`, `failSaves(fn)` to act like a full disk, `forget()` to empty the cache) and `window.__sync` (`state()`, `syncNow()`) help tests; older suites that read `localStorage["98ish.fs.v1"]` must read `await window.__drive.exportDrive()` instead (same shape).

## Uploads kept as they are + big media on the device (wave 2, 2026-10-08)
- **The rule** (`utils/mediaRules.js`, pure, `mediaRules.test.js`): songs, videos and PDFs come in untouched. The old 30-second mono WAV cut (`fileTransfer.audioToWav`) and `uploadInto` are gone; `convertUpload` only handles text, web pages and pictures now (pictures are still made phone-sized: PNG <= 1600 px from My Computer's converter, JPEG <= 2048 px through `receive.js`, deliberate for the sync budget).
  - <= `INLINE_MEDIA_BYTES` (8 MB): a data URL in the drive like a photo; syncs when its folder syncs (sync's per-file limit is 12 MB of text = 9 MB of bytes).
  - Bigger: a **media reference** `98ish-media:<key>;<mime>;<bytes>` as the file's text (inline in the index, < 300 chars) and the bytes as a **Blob** in the drive database's new `blobs` store (`DB_VERSION` 2; `driveStore.js` `mediaRef`/`parseMediaRef`/`mediaKeysIn`/`blobsToDelete`, `putBlob`/`getBlob`/`blobKeys`, `commit({ blobDeletes })`). Never turned into text, never uploaded: "device only".
  - Caps (`MEDIA_CAPS`): song 300 MB, video 2 GB, PDF 200 MB, and never more than `navigator.storage.estimate()` says is free minus 20 MB (`FREE_ROOM`). Without IndexedDB (private windows) only the inline size fits.
- **fs.js**: `storeMedia(blob, { mime })` (writes the Blob first, then the caller writes the reference with `writeAndSave`; a new key is held 10 min (`MEDIA_HOLD_MS`) so a save in between doesn't collect it), `mediaBlob(file)` (Blob for a reference or a data URL; the newest 6 Blobs cached: IndexedDB Blobs are disk-backed, not memory), `peekMediaBlob` (synchronous, for Send To from the tap), `file.deviceOnly` / `isDeviceOnly` / `mediaInfo`. Every save collects unreferenced Blobs in the same transaction (Recycle Bin references keep them). `byteSize` of a reference = the real bytes, so Drive C: Properties and quotas are right. `driveSummary().deviceOnly` counts them. Erasing the drive deletes the whole database, Blobs included.
- **Saving** (`utils/mediaFiles.js` `keepMediaFile(dir, file, { kind })`, `mediaFolder(kind)`: C:\My Music, C:\My Videos (new default folder), C:\Documents for PDFs): used by `receive.js` (Upload from Phone, dropped files, Compass downloads, the share target), Music 98's `importSongs` and Media Player's `importVideos`. The result's `note` ("X (12 MB) is kept on this device only: files over 8 MB aren't synced or included in backups.") is shown by every caller.
- **Sync** skips them: `syncPlan.staysOnDevice(item, maxFile)` (device-only or text over `maxFile`) feeds `driveSync.push`'s "too big" set; status text "N files are too big to sync: they stay on this device." **Backup** writes only the reference (restored on the same device it still plays; elsewhere the file says its contents aren't on this device) and Backup's message counts them. Download/Send To give back the original Blob; a folder .zip includes them up to 200 MB each. Come Over (hand a file, shared folder) and Network Neighborhood refuse them with a "use Send To > My Phone" message; Mail's attachment size check already refuses them by their real size.
- **Budget math:** nothing new goes online. Inline media is bounded by the existing per-account sync quota (300 MB with the bucket) and the 750 MB bucket total; My Music/My Videos aren't default sync folders. Device-only media costs no Atlas, Render or Blob budget at all.
- **iPhone Safari limits (researched 2026-10-08; WebKit storage policy since Safari 17 / iOS 17):** each origin may use up to about 60% of the disk in Safari (the browser app); a Home Screen web app gets its own, similar origin quota on iOS 17+ (older iOS: about 1 GB with prompts beyond); `navigator.storage.estimate()` reports the quota, `navigator.storage.persist()` exists since iOS 15.2 and is granted to Home Screen apps (Safari tabs usually get `false`). Without persistence, Safari deletes all script-writable storage (IndexedDB included, so device-only videos) after 7 days of Safari use without a visit; Home Screen apps are exempt. IndexedDB Blobs are supported (stable since iOS 14). So: big media should live in a Home Screen 98ish, and Help tells people to keep their own copies of device-only files. Not yet tried on a real iPhone: a 1 GB video import (Safari copies the File into storage; time and memory), Blob playback after the app was evicted from memory.
- **Upgrading:** opening `98ish-drive` at version 2 runs `onupgradeneeded` (adds `blobs`); a tab still running the old version closes its connection (`onversionchange`), and an old version opening a version-2 database gets "can't open your files" until it reloads.

## Version history (wave 3, 2026-10-08)
Previous versions of Notepad, WordPad and Paint files ("Restore Previous Version...").
- **Pieces:** `utils/versionsCore.js` (pure: caps, `addVersion` (skips empty, same-as-newest and too big), `enforceCaps`, `moveFile`, previews, copy names), `utils/versionStore.js` (factory over IndexedDB: `meta` holds the index, `data` each version's text by id; one transaction per change), `utils/versions.js` (the app's instance, imported eagerly in `main.jsx`), `shared/versions/PreviousVersions.jsx` (list newest first, a preview of the words or the picture, **Restore** / **Save a Copy** / Close).
- **How saves get there:** `fs.writeAndSave` hands every overwrite of a `text`/`note`/`richtext`/`image` file to the keeper (`setVersionKeeper`) once the new contents are saved (WordPad, Paint, Save As over an existing file, a restore itself); Notepad, which sets `textContent` itself, calls `keepVersion(file, old)`. A restore writes through `writeAndSave`, so the contents it replaced become a version (a restore can be undone).
- **Where:** File > Restore Previous Version... in Notepad, WordPad and Paint (after the unsaved-changes prompt), My Computer > Properties > "Versions:" row, and the desktop file menu (right-click / long-press) of versioned files.
- **Following files:** versions are keyed by path, but each path is tied to its `File` object; after drive changes (`onFsChange`, 400 ms debounce) a renamed or moved file's versions move with it, a file in the Recycle Bin keeps them, and a file deleted for good loses them. At start (`watchFiles`, 4 s after load) paths that no longer lead anywhere and aren't in the Recycle Bin are cleared.
- **Caps** (`VERSION_CAPS`): 10 versions per file, 7 days, 6 MB per version (bigger isn't kept), 16 MB per file, 64 MB in all (the oldest of any file go first). Device-only: never synced, uploaded or in a Backup, so no server or budget cost.
- **Privacy:** the database is named through the storage seam: `keyPrefix() + "versions"` (`98ish.versions`, `98ish.u.<id>.versions`); `onUserRemoved` deletes a removed profile's database; Delete My Account with "erase this device" calls `eraseVersions()` (`utils/account.js`). Help: `previous-versions`, a privacy-device row, a privacy-delete row, delete-account.
- **Tests:** `node --test client/src/utils/versions.test.js` (10: 10/7-day caps, same/empty/too big, per-file and total caps, sizes, moving, previews, the IndexedDB store round trip and expiry on reload, restore round trip, one database per user + erase, no IndexedDB). Browser (scratchpad `scan/vg-e2e.mjs`): Notepad Save As, change, Save, then File > Restore Previous Version... lists one version with its preview, and Restore puts "alpha version" back in the editor and on the drive; a rename keeps both versions; a picture's version opens from the desktop file menu with its preview.
